# Playlist editing: design

Status: built, 2026-11-20 (PR #163, epic RE-44). Covers building, editing and publishing playlists on relisten-web. The API side is specified in RelistenApi: [`docs/design/2026-11-18-playlist-guide-content.md`](../../RelistenApi/docs/design/2026-11-18-playlist-guide-content.md) (descriptions, Markdown subset, timestamp links) and [`docs/design/2026-11-18-playlist-sharing.md`](../../RelistenApi/docs/design/2026-11-18-playlist-sharing.md) (publishing, following, copies, reporting).

## Decisions

- **Writes go from the browser straight to the User Service**, same origin: `POST /v1/playlists`, `POST /v1/playlists/{id}/operations:batch`, `PUT /v1/playlists/{id}/publication`, `POST /v1/public-playlists/{code}/reports`, with a CSRF token from `/api/user/v1/csrf` in `X-Relisten-CSRF`, fetched for each write (nothing cached for the page's life; cache it if that ever shows up as slow). The relisten.net ingress, the preview gateway and `pnpm dev:session` (`vite.session.ts`) route these paths. A server action is used only where the web server itself has work to do: after publishing or unpublishing, it clears the public page's cache (`revalidateTag`), for the signed-in owner's own playlist only.
- **Edits are an operation log.** The draft is a `PlaylistContent` in an external store (`src/playlists/store.ts`, `useSyncExternalStore`). Every change is an operation with a client-generated TypeID, applied optimistically by one pure `applyOp(content, op)` that mirrors the server's evaluator (both run the shared vectors in `src/domain/__fixtures__`, as do the TypeIDs), and sent in batches held to the base revision. Saving is an xstate machine (idle, sending, rebasing, failed), one batch in flight at a time. Every edit sends at once: text fields commit when they close, so there's no typing timer. On a revision conflict the store refetches the snapshot and replays its pending operations (they address IDs, not positions). A refused batch (422) is dropped and reverts, and the store hands back its operations, so the editor reopens the field they came from with the reason. Every field's text reaches the playlist one way (`commitText`): decided against the store's content as it is, with the store saying whether the edit applied, so text is always saved, waiting in a field, or discarded on purpose. Refused text waits its turn: it shows in its field when no other field is open (never in place of one), and it's sent again only when you close it after changing it. Anything else (offline, signed out) keeps the edits for Retry. Whatever needs the server caught up with the screen asks one thing, `settle()`, which says how the save ended (saved, failed, refused): Publish and Done wait on it and say why when it didn't save; an editor closed any other way (the nav bar, Back) with a save on its way waits on it, then re-renders the page it landed on. What the server hasn't rendered or looked up yet (edited prose, a track another tab added) is decided in one place, `unresolved()` in `rows.ts`: the editor marks it and, after a save, asks the server for it. Each operation records its inverse, which is undo; the server never reuses an ID, so an undo that re-creates something names it anew and older undo steps follow (`remapIds`).
- **Positions are anchors.** The API places entries and segments `after`/`before` an ID and computes ranks. Tracks added together (a show's tape, Twist → Jam) go in as one segment, so they stay together under shuffle.
- **Markdown renders on the server only.** One sanitizer (CommonMark via satteri, no GFM) walks the tree into React elements over the guide subset: paragraphs, bold, italics, lists, block quotes, `##`/`###` headings, `https:` links, `#t=` / `#entry=…&t=` links, single newline as a line break. Everything else renders as text; no `dangerouslySetInnerHTML`. Bare timestamps link only in track descriptions and only within the track's length; a link to an entry that can't play is text. The shared vectors (`RelistenUserServiceTests/Fixtures/playlists/guide-markdown-vectors.json`) run in vitest. satteri is native, so it's external in the server build and traced into the output (`timber.config.ts`, `nitroConfig.traceDeps`).
- **The flow is one column of rows** (`flow.ts`). Every row is a rail cell and a content cell, and rows sit flush: spacing is rows too. Each rail cell draws only its own stretch of the line (from the first track's dot to the last's), so no row can break the rail. A section is its rows' content cells, tinted and cornered by position.
- **The editor is the read view in edit mode, laid out the same.** `/account/playlists/[playlistId]/edit` renders the same article (`PlaylistArticle`), with the same rows, from its draft, so opening it moves nothing. Its controls take no room. A card's Edit menu sits in the read view's ⋯ place. Each undescribed segment of two or more entries is outlined as a group, drawn over its rows, with its label on the top border (what drags it) and its menu at the corner, as a section has. A text block has no menu: clicking it opens it, and its field's toolbar has Move Up, Move Down and Remove. The editor adds rows only for what's being written and the Add zone at the end. Rows are laid out from a deferred copy of the draft, so each edit commits as a transition and rows slide to their new places (`ViewTransition`; off past 150 rows).
- **Prose is edited as written.** Click a block (description, section comment, text, note) to edit it in place, in a textarea in its own type (`MarkdownField`): ⌘B/⌘I/⌘K, a pasted `https:` URL over a selection becomes a link, and **Insert Timestamp** picks a track and a moment. The field keeps its own undo history (edits go through `setRangeText`, not the deprecated `execCommand`). Once saved, `router.refresh()` brings back the server's render; until then the block shows its text as written, marked pending. No rich-text library: the stored text is exactly what the author typed.
- **Drag and drop is Pragmatic drag and drop** (native drag events), and a drag changes no layout. A row drags from anywhere on it, and a section or group by its label (each is made draggable when a press lands on it, never in a text field). Every row says where a drop on it lands (`flow.ts`): by its top or bottom edge, next to it (inside its section or group, or on its own next to a lone track or text), and by a card's middle, grouped with it; the space between rows lands between them. While a drag is over a row, it draws a line at that edge (or outlines the card) with a label ("Move here", "Move here, on its own", "Group with this") over the rows. A drop that would change nothing (`dropOps`) shows nothing. Every move is also in the menus (**Move Up**, **Move Down**, **Move to Its Own Group**, **Move to Section**), the keyboard's and screen reader's way.
- **Tracks get in from where people listen.** **Add to Playlist** in every track's and show's ⋯ menu and on show pages (a tape), with **New Playlist…**; each is one request, with a toast offering **Open** and **Undo**. The menu loads your playlists each time it opens. Adding tracks from inside the editor waits for real track search (see Not in scope).
- **Publishing asks first.** The **Publish** control (Private, Published, Taken Down) copies the link once published; **Preview as Public** shows the reader's view before then. Public pages have **Report**. Link previews are an OG image (`/playlists/<code>/opengraph-image.png?v=<revision>`): name, owner, artists, length, never prose.

## Boundaries

Each part has one job and a fixed direction of imports. The lint layering in `oxlint.config.ts` enforces it (`src/playlists` has its own rule, like `src/player`'s; a feature can't import `../`, so the editor's files sit flat in `src/features/playlist`).

| Part                     | Where                                                                      | Owns                                                                                    | Never                                  |
| ------------------------ | -------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- | -------------------------------------- |
| Wire and operation types | `src/domain/playlists.ts`                                                  | Snapshot, operation, publication and receipt shapes                                     | Logic                                  |
| Operations               | `src/domain/playlistOps.ts`, `src/domain/typeid.ts`                        | `applyOp`, inverses, TypeIDs. Pure, no React, no fetch                                  | Network, UI                            |
| Guide Markdown           | `src/lib/guideMarkdown/`                                                   | Parse and sanitize (server), auto-link timestamps, render with a `renderSeek` callback  | The player, fetching, editing          |
| Playlist service         | `src/playlists/` (client)                                                  | Transport (CSRF, batches, retries with the same IDs, errors), the draft store, commands | Importing features, the shell, `data/` |
| Read views               | `PlaylistArticle`, `flow.ts`, `rows.ts`, `blocks.ts`                       | The article, its rows and rail; slots for the editor                                    | Importing the editor                   |
| Editor                   | `PlaylistEditor`, `MarkdownField`, `editOps`, `dragOps`, `usePlaylistDrag` | Menus, the composer, drag wiring; menu actions and drops as pure, tested operations     | Its own copy of a read-view component  |
| Add to Playlist          | `src/player/AddToPlaylist.tsx` calling `src/playlists`                     | The menu, the New Playlist dialog, their toasts                                         | The draft store                        |

Server-only data (`src/data/playlists.ts`, `load.ts`) is the read path: the server resolves tracks and sanitized prose, and `playlistView` builds rows from any content (the server's, or the editor's draft). The client never imports `src/data`.

## Not in scope

Each of these is its own task if it's wanted, filed with `--discovered-from`:

- Real-time collaboration, multi-tab sync, offline queues that survive a reload.
- A rich-text or WYSIWYG editor, image embeds.
- Dragging between pages or windows, a playlist tray.
- Following and copying UI (the sharing doc), and moderation tooling.
- Waveforms, timeline markers on tracks.
- Add to Playlist from the player bar (it has no menu today; the now-playing list's ⋯ has it).
- Adding tracks from inside the editor. It was built (song search, then a performance, or a pasted link) and removed: without real track search it wasn't worth its bugs. It comes back with search (RE-54).
